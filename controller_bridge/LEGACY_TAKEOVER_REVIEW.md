# 一代自动接管参考查证（2026-11-11，只读）

## 结论修正

用户指出一代能由示教器直接接管后，扩大到控制器的旧工程目录检查，
找到了 **一代 JEServer 源码及其实际构建产物**，不是完全没有实现可参考。
之前只检查 SDK 头文件、二代工程及有限文件名候选就结束调查，范围不足。
“没有公开前置回调，所以只能等厂商提供接口”的结论过强，应改为：
先查证 SDK 自己已有的伺服状态切换及旧插件如何处理失去控制，再确定二代迁移方法。

**这份调查不是自动接管实现或实机验收。没有停止进程、加载库、执行机器人 API、

## 一代源码与实际旧库确认的行为

1. **Switch=true 是重初始化，不是优先级握手。**
   源码 566–595 行先调用 `ClearRobotError`；true 分支逐机器人执行
   `RobotStopRecover → ServoEnd → RobotPoweroff → 等待100ms → RobotPower → ServoStart`。
   false 分支执行 `ServoEnd → RobotPoweroff`。这些不能照搬到二代的无自动清错/上下电设计。
2. **普通 Joint 不做二代所有权校验，也不检查 SDK 返回值。**
   源码 663–669 行构造关节后直接调用 `ServoJoint`，随后继续处理其它数据。
   实际安装旧库的只读反汇编也显示调用后没有使用返回寄存器做错误分支，直接继续处理。
   此订阅分支本身没有每条轨迹的开始/结束或主动归还所有权握手。
3. **旧版确实有驱动故障停止，不是完全无保护。**
   源码 351–391 行的 `stop_on_joint_driver_error` 检查 `IsRobotDriverError`，
   遇正数驱动错误会对机器人调用 `RobotStop`；没有错误时清除本地重复停止标记。
   因此不能把一代概括成“所有故障都忽略”。
4. **队列行为不同。**
   源码 823–829 行为命令 SUB 设置 `rcvhwm=1`、`conflate=1`，同时订阅 Switch/Joint 等。
   这会丢弃中间消息，不构成可靠的控制权握手；二代不能为模仿一代而丢失启停顺序。

这些事实能解释为何旧进程在 SDK 改变运动状态或拒绝伺服写入后仍然在线，
但仅凭它们不能证明所有接管场景都无冲突，也不能证明用户本次 state_error 的首发字段。

## SDK 本身已有的执行状态检查

只读检查当前 SDK 的符号与反汇编，没有加载或调用 SDK：

- `ServoJoint` 入口先调用 `get_robot_state`，与 `0x0d`（13）比较；
  不相等时直接返回，不进入后面的伺服目标写入路径。
   该早退分支保留当前状态作为返回值，状态为 0 时也可能返回 0 而没有写目标；
   所以不能只靠 `ServoJoint` 返回 0 判定 ROS 仍持有有效伺服控制。
- `get_robot_move_state` 在这份二进制中直接跳转到 `get_robot_state`。
  因此现有反馈的 MoveState 与这个入口检查有关，不必臆造另一个未确认的状态查询 API。
- `robot_teach_joint` 先调用 `get_robot_busy_state`，非零时返回拒绝；
  允许时调用 `recover_robot_move_state`，然后进入 `axis_movej`。
  这说明 SDK 本身已有状态判断，**不等于点动在任何 ROS 运动阶段都一定抢占成功**。
- `recover_robot_move_state` 有内部状态/命令操作，不能把它复制为 ROS 的自动故障恢复。
- `ServoEnd` 设置其伺服线程结束标记并等待；单看这些代码仍不能把它当作安全制动证明。

13 的含义来自**当前固定 SDK 二进制的具体实现**，不是已经取得的跨版本公开协议保证。
不能仅凭一个未识别状态值、位置变化或任何 state_error 就宣布“示教器正常接管”。

### 继续查证：入口拒绝新目标，不等于后台执行线程已退出

进一步只读检查同一 SDK 的 `_servo` 与 `servo_execution`：

- `_servo` 调用 `servo_execution`，结束后才进行 SDK 线程结束处理。
- `servo_execution` 入口要求当前状态为 0，然后设置为 13（地址 0x121fb0–0x121ff2）。
- 循环检查自己的结束标记、SDK order、驱动错误及负数运动状态；
   不是每次只要状态不等于 13 就退出（0x122058–0x1220e0）。
- 同一循环仍有 `SetGroupCtrlTarget` 的目标输出路径（0x122b1c），
   退出路径还会调用 `set_robot_state` 写回状态（0x122c85）。

因此上一节的 `ServoJoint` 入口检查不能单独证明旧伺服输出线程已经停止，
更不能作为直接执行 `owns_servo=false`、绕过所有 Stop/End 的依据。
也不能先让其它运动开始、随后盲目 `ServoEnd`，就假定退出路径不会影响新运动状态。
这些是静态路径事实，不是已经观测到两线程在实机同时输出的证据。

## 与二代当前行为的差异

二代 [原生核心](mk2_control_core.c) 在拥有伺服时检查电源、驱动错误、运动错误、
状态及位置边界；触发状态保护会进入锁存故障，并经 `mk2_core_stop` 调用 Stop/End。
本机 [共享时钟节点](../src/mk2_shared_clock_control_node.cpp) 发现硬件退出 ACTIVE 后，
终止控制栈，避免 JTC 在旧状态上继续接受目标。

因此应重点检查：SDK 是否已经切换了执行状态，而桥仍以为自己拥有伺服，
随后调用全局停止打断了新控制源；或者这次其实是真正电源/驱动/运动错误。
这两种情况不能用统一的“忽略 state_error”处理。
之前新增的 `first_state_error` 会保存触发保护前实际使用的输入，但诊断插件尚未部署，
不能追溯补出已经发生的异常。

## 迁移方向与尚缺验证

可继续研究 SDK 原生切换，而不是先要求用户增加接管按钮：

1. 明确正常 SDK 伺服失权的状态、返回值及其与真实故障的区别，先在隔离 SDK 仿真中验证。
2. 只有 SDK 已确认退出 ROS 伺服且状态健康时，考虑进入独立的让位状态，
   停止 ROS 目标写入、终止当前目标、丢弃旧目标；不能继续用旧目标抢回控制。
3. 不对已经交给其它控制源的运动盲目调用全局 Stop/End；
   但真实驱动故障、强停、断流和未知状态仍必须保留原有保护。
4. 重新接管必须以新反馈与新执行请求开始，不自动清错、恢复强停、上下电或重放旧轨迹。
5. 确认“SDK 执行状态转换”不等于已经证明“ROS 正在运动时按一下点动键必然立即优先接管”。
   该行为以及停止次序、旧目标不会回写，均需仿真与之后的授权实体验收。

## 后续源码调整：补齐判断所需的诊断（尚未部署）

已在 [核心](mk2_control_core.c) 和 [适配器](mk2_control_plugin.c) 增加
`Bridge.servo_observation`，不改动原有所有权、停止、看门狗或故障判定：

- `seen_servo_state`：ACTIVE 且本地仍拥有伺服时，是否见过有效位置采样的状态 13。
- `first_active_nonservo_sample`：同一会话见过 13 后，首次见到非 13 的输入，保存时间与完整采样，
   在原有保护可能调用 Stop/End **之前**仅做内存复制。
   尚未见过 13 时不冻结“偏离”事件，避免启动时的状态 0 遮蔽之后的真正变化。
   新的有效伺服启动尝试重置这组会话诊断；这不复位故障或放宽启动条件。
- `last_sdk_call`：最后一次 `ServoStart` / `ServoJoint` 的返回值、阶段、命令时间，
   以及执行该命令时校验使用的输入；在原有 SDK 错误清理 **之前**保存。
   `command_validation_sample` 不是 SDK 调用后的额外采样，也不是与 SDK 返回值原子同步的状态。
   首条命令的 Start/Joint 共用这一份调用前校验输入。
- `ownership_evidence=false`：明确以上均不能当作示教器已获权、线程已退出的确认。

正常状态 0 与 SDK 返回 0 可能同时存在而没有目标写入，诊断不会把它改判成已安全接管。
任何真实故障仍按原规则停止并锁存；故障后不自动清错、重试 SDK 或重新接管。
故障日志在停止后输出冻结输入，原有 `first_state_error` 日志格式保持不变。
`Robot0` 仍然是当前真实反馈，不用冻结诊断冒充当前位置。

这不是原仿真启动器：原入口仍禁止与实体同时启动，未修改或绕过其锁与进程检查。
这里是独立的 SDK 研究进程，不运行 RobotMain、不加载通信插件。最初版本只有隔离预检和
无运动初始化入口；下文单独列出后来增加的显式虚拟运动模式。

### 显式虚拟运动对照：三组实际完成

2. `--end-jog`：先结束伺服，再发出相同点动请求。
3. `--stop-end-jog`：先请求停止当前运动，再结束伺服并请求点动。

独立只读复核确认三份实体配置 SHA 仍等于原基线，未发现 RobotMain、主站或沙箱探针残留。
全程只有虚拟动作，没有实体动作或插件更新。

**结论范围：**当前 SDK 的直接 `robot_teach_joint` 调用在正常保持伺服状态 13 时没有自行抢占，
即使全局 busy=0，也返回 13；先结束伺服后同一调用可以产生虚拟位移。实验进程退出 0 仅表示
对照按计划完成，不代表第一组接管成功。第三组没有省略 End，不能据此认定 StopRun 单独足够。
本次保持目标不动，也不证明运动中停止距离或实体制动行为。

仍需核查现有示教按键的网络分发路径是否在点动调用前执行了其他停止/结束操作；
不能把直接 API 对照扩大为“真实示教器一定没有自动接管”或“一代不可能自动接管”。
生产实现还必须同步撤销 PC 轨迹/命令流，并避免旧会话延迟 Stop/End 影响新的示教运动。

### 现有示教按键网络路径：服务器侧静态核查

只读核查同一固定 SHA 的实际 SDK，以下为 ELF 内虚拟地址，不是运行时地址：

| 通道 | 入口和分发 | 点动处理 |
| --- | --- | --- |
| 默认 TCP6666 | `TeachServer` 0x163350 → `btnevent_action` 0x159dc0 → `teach_code_deal` 0x163660 | 文本片段以 `t` 开始，`teach` 0x163590 解析 `v` 至 `!` 间十进制整数；点动分支 0x15a2f0 直接调用 `robot_teach_move` |
| 默认 TCP6667 | `TeachServerCmd` 0x163410 → `command_action` 0x15c7a0 | 按二进制协议的 `function` 字段分发，`robot_teach_move` 调用在 0x15f2d3，`robot_teach_joint` 调用在 0x15f386 |

6666 的关节轴 0..6 正向整数值依次为 49、50、51、52、53、54、55；负向依次为
113、119、101、114、116、121、117。这是服务器映射，不是已确认的实际 UI 按键映射。
整数 33 等值进入独立停止分支，在 0x15a231 调用 `robot_teach_stop`；点动分支本身
不先经过停止，也不检查点动返回值。解析器支持连续处理多个片段，所以仍不能排除客户端
把独立停止和点动组合发送的可能。

6667 点动分支解析 `axis_index:int`、`dir:int`，调用后通过 `PushFeedbackDataInt` 回传结果；
`robot_teach_stop` 则是独立的 `function` 分支，调用在 0x15fb7f。
检查的两条服务器点动路径都没有自动前置 `RobotStopRun`、`ServoEnd` 或 `robot_teach_stop`。
通用 TCP 输入回调层也未发现这些前置调用。

`robot_teach_move` 0x1684f0 在关节坐标模式下直接尾调用 `robot_teach_joint` 0x167dc0；
后者在 busy 检查后调用 `recover_robot_move_state` 0x133ac0，再调用 `axis_movej`。
这个 recover 只在状态 7/0 时设状态 0，随后设置 order=0，**没有把状态 13 结束为 0，也没有
等待伺服线程退出**。`robot_teach_stop` 0x167960 则经 `robot_move_stop` / `set_robot_move_stop`
设置 order=1，并不是 `ServoEnd`。不能把这两个操作都统称为已经完成安全交接。

远端厂商 `TeachComm.cpp` 示例的 202–216 行设置机器人/坐标，225–247 行构造速度和点动，
249–255 行在另一个触发条件下构造独立停止，306–309 行发送编码数据。它不是已确认的生产
示教器 UI 源码，没有证据说明实际 UI 与示例发送顺序一致。示例使用 `SetProtocolDataString` /
`SetProtocolDataInt` 等厂商编码接口；6667 是带长度、名称哈希、CRC 和帧标记的二进制协议，
不是可直接发送函数名或 JSON 的接口。

**尚缺证据：实际现有示教器按键发送的完整命令顺序。**现有 SDK 日志只能证明进入过
点动函数，不能证明请求成功，也不包含轴和方向；6667 的返回值有助于判定请求结果。
检查的公开 Teach/Comm 头文件中没有找到可注册的“原生点动前等待让权”通知接口，
但这不证明必须修改厂商 SDK：透明协议仲裁仍是待评估方案，需保持原按键和接口、严格校验协议、
隔离旧 PC 会话并验证失败关闭行为，不能仅看到按键日志就异步结束伺服或重放运动命令。

### 原生协议处理器隔离对照：四组实际完成

新增 `--protocol-compare`，四组仍各用全新私有 SDK 会话：
`--button-jog` / `--button-end-jog` 对比伺服中与先 End 后的文本按键处理；
`--command-jog` / `--command-end-jog` 对比相同条件下的厂商二进制命令处理。

文本使用完整 `tv49!`（轴 0 正向），显式选择机器人 0、关节坐标；二进制通过 SDK 原有
`SetProtocolDataString` / `SetProtocolDataInt` 构造 `robot_teach_move`、`axis_index=0`、`dir=1`，
逐帧验证后交给原生 `command_action`。文本交给原生 `btnevent_action`。
两个入口实际 ABI 为 `int(int fd)`，静态核查均只接收一次，不要求 TCP 地址族或已注册 fd。
因此试验用私有 AF_UNIX `socketpair` 先完整排入短命令，再调用回调，记录请求 hex 和接收长度；
不连接实体端口，也不依赖沙箱 loopback 是否 UP。

**回调返回的是接收/处理长度，不是运动成功码。**试验明确分开标注，仍以实际/目标位置和运动
状态观察结果，并用先 End 后的组验证协议请求确实有效。6667 的整数反馈入 SDK 队列，
本试验不把 socketpair 当作反馈服务器。这只是实际协议处理器的集成对照，不覆盖完整 TCP
半包重组、实际客户端发送顺序或生产透明仲裁。

新增模式严格编译、主机加载前拒绝以及控制器隔离预检通过；最新预检目录

### 离线仲裁策略原型：已测试，未接入生产

新增仅位于测试目录的 [代次仲裁模型](tests/priority_session_model.h) 和
[离线测试](tests/priority_session_model_test.c)，没有 SDK、ROS、网络或硬件依赖。
它不是自动接管功能的已部署实现，也没有改变现有控制核心的任何保护条件。

- 只有当前服务器代次可接收 PC 的 Start/Joint/Release/Stop/End；有效原按键请求到达时，
   在开始异步让位前先失效旧代次。旧 ROS 清理命令不能因迟到而打断新的示教运动。
- 必须同时具备新鲜健康状态、PC 命令流静默、旧写入者已退出以及静止证据，才允许仍然新鲜的
   按键请求转发一次。证据不足继续等待，不把状态不等于 13 或某个 API 返回 0 当作退出证明。
- 松开/停止取消尚未转发的请求；过期请求不补发；交接超时、时间回退、真实故障和代次溢出锁存失败。
- 按键松开本身不表示机器人已停稳。后续 ROS 获取必须等待独立合格空闲证据，并执行新代次握手，
   不允许旧 Switch 自动重夺控制。

15 个离线场景严格 C11 编译通过，ASan/UBSan 通过；普通测试二进制只依赖 libc。
场景覆盖所有五类旧 PC 操作、三种单独缺失的交接证据、松开取消、过期不重放、硬超时、
故障锁存、只转发一次、新代次获取、非法/过旧/未来请求、重复按键、时间回退、代次溢出和启动门禁。

**尚未解决的生产边界：**模型假定未来适配层串行保护全部 SDK 修改入口，验证协议和请求新鲜度，
并真实建立上述交接证据。当前旧 Switch/Joint 协议没有该代次字段，模型没有给它伪造证据，
也没有把当前插件改成忽略 SDK 状态。实际按键入口、完整协议流重组、松开/断连停止保障、
故障急停旁路、PC 轨迹撤销与原生会话隔离均须单独实现和验收。

在已知控制器工程目录中仅定位到厂商 `TeachComm.cpp` 示例，没有找到实际生产示教 UI 源码；
不能从示例推定实际客户端的完整命令顺序。下一步需要确认现有示教界面的运行设备与程序位置，
优先只读检查客户端，而不是让用户在未接管的实体伺服状态下反复按点动键试错。
