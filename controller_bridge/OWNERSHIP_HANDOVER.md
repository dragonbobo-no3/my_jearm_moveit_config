# 示教器 / MoveIt 显式交接（源码阶段，未部署）

## 最新需求：现有示教器点动键直接优先接管（尚未实现）

**一代查证更新：**现已在控制器旧工程找到 JEServer 源码，并核对其构建库与实际安装库哈希相同。
SDK 自己已有伺服状态检查，旧桥又不检查 ServoJoint 返回值；因此此前“只能等厂商提供前置接口”
的判断过强。应先验证 SDK 原生切换与桥的失权处理，不能把下面的接口缺口描述当作已经排除这条路径。
原始证据、旧版自动清错/上下电风险及待验证项见[一代接管查证](LEGACY_TAKEOVER_REVIEW.md)。

**继续查证：**SDK 的 `ServoJoint` 入口拒绝新目标，不等于后台伺服线程已退出。
后台线程有自己的结束标记、SDK order 检查及目标输出路径；不能仅凭状态不为 13 就
放弃本地所有权或跳过保护。源码已补 `Bridge.servo_observation`，记录首次非伺服状态输入和
最后 SDK 调用结果；仅为诊断，明确 `ownership_evidence=false`，不执行自动让位。
新增 11 个替身场景、原有 12 个首发状态场景与实际 JSON 回归均通过，详见上述查证记录。
这项诊断尚未部署，不能补出过去异常的首帧，也不能代替自动接管验收。

后续已实际尝试独立真实 SDK 沙箱初始化：五类命名空间、无硬件/外网、只读主机、
空插件与加载前拒绝检查通过；SDK 因当前 `RLIMIT_RTPRIO=0` 无法设置实时调度，
`system_initialize` 返回 -11。尚未进入点动/伺服实验，不能把沙箱预检成功当成接管成功。
未补丁绕过 SDK，未重启实体；详见[真实沙箱探测结果](LEGACY_TAKEOVER_REVIEW.md)。

用户进一步选择：**示教器优先级高于 ROS；按现有点动键直接触发 ROS 退让**。
用户明确不接受新增接管按钮、IO 或单独接管请求后再点动的交互。
该需求取代下面的“忙时拒绝”，不是当前手动 shared 代码已经提供的行为。

期望顺序是：识别示教器运动意图 → ROS 取消目标并拒绝新目标 → 受控停止当前运动、
确认停稳并退出 ROS 伺服 → 放行示教器运动。ROS 被抢占的旧轨迹不自动续跑，
急停/故障保护不受优先级规则屏蔽；示教器结束后不能复用旧 ROS 目标或缓存位置。
仅停止 ROS 发布线程还不够，必须明确控制器确认了伺服退出；也不能在示教器已运动后
再调用全局 StopRun，假定该调用只影响 ROS 运动。

本次再次核对 SDK 声明：`get_robot_move_state` 是汇总运动/异常/强停状态，
不是“示教器即将点动”的前置意图；`ServoEnd` 仅说明关闭伺服，不承诺运动安全停止，
`RobotStopRun` 停止机器人当前运动，也没有按控制源隔离的声明。
因此轮询运动状态、位置偏差或 state_error 后退让，都不能证明未发生并发或未停止示教器自身运动。
若 SDK 原生切换不能提供足够保证，才仍需在既有示教器分发路径中取得前置接管请求、
协调执行或取得厂商支持接口。现有公开头文件尚未找到此类前置回调，但新发现的一代通信插件源码
已经提供了比较 SDK 原生状态切换的依据；此前“只有二进制和头文件”的材料范围描述现已更新。

本次仅更新需求和接口边界，未改变运行控制逻辑，未部署或操作实机；不能宣称已支持直接按键抢占。

## 之前的需求：双入口在线，忙时拒绝（已被示教器优先取代）

用户明确选择：**先到先执行，已有运动时拒绝新操作，不抢占、不排队、不自动重放。**
这与下文已有的手动 shared 交接不是同一个功能，不能宣称现有 shared 已满足该需求。

目标语义：
- 空闲时示教器或 MoveIt 的第一个有效运动请求在同一个控制器级入口原子获权。
   启动 MoveIt、打开 RViz 或仅有后台保持流，都不应抢先占用空闲控制权。
- 已有操作期间，新操作立即返回 BUSY；同一操作的点动续帧/轨迹采样不算新操作。
   两个入口同时到达也必须最多成功一个，不能用分别轮询 MoveState 来替代原子仲裁。
- 当前操作完成/取消后，确认停稳并完成伺服释放，才恢复空闲；下个请求重新读取实际位置。
   当前 JTC 持续保持和手动释放机制不能直接当作自动归还实现。
- 急停、保护停止等安全入口独立保留，不能因 BUSY 而屏蔽；故障不得自动清除或抢占恢复。

已只读核对的接口事实：SDK 的 `robot_teach_interface.h` 声明了
`robot_goto_joint`、`robot_goto_cartesian`、`robot_teach_joint`、
`robot_teach_cartesian` 等直接运动入口；`ExternalPlugin.h` 提供通用外部功能调用，
`TCPConcurrentServer` 提供另建 TCP 服务的回调。**这些都不是既有示教器服务的前置命令过滤器。**
`set_robot_run_type` 在头文件中指实体/仿真选择，不是控制源互斥开关，不能拿它替代仲裁。
在此前检查的可用头文件中，没有找到受支持的示教器执行前 veto/BUSY 回调。
目前 SDK 内部的示教器命令分发源码仍未找到，但已找到一代通信插件源码，
不能再把这两种源码或“没有前置回调”与“没有原生状态切换”混为一谈。
旧 BUSY 方案的接口调查也不能直接当作最新示教器优先方案的不可实现证明。

**继续实现所缺的输入：示教器 TCP 命令服务/控制器分发层源码，或厂商支持的
执行前过滤/统一控制源仲裁接口及 BUSY 响应协议。** 如果走统一网关，则两条实际运动路径
必须都接入且不能绕过；也需有明确的示教器协议与可配置的后端入口，不能只新增一个无人经过的服务。
仅增加 ROS 锁、轮询 SDK 状态、屏蔽 state_error、二进制注入或替换未知协议响应都不构成已验证实现。
本次没有安装、重启、切换模式或发送机器人命令。

## 操作接口（完成构建、授权部署与验收后使用）

- 选择 `hardware_mode:=shared`；实体后端再选择 `mode:=real`。
  `confirm_enable:=true` 仍为显式允许后续接管的条件，不代表启动立即使能。
- 启动为 `UNAVAILABLE`。监督器确认硬件 `lh_mk2_system` 和
  `jearm_controller` 均 inactive，并收到有效 guarded 原生反馈后，才发布 `PENDANT`。
  这期间不发送 `Switch=true` 或轨迹；示教器可以保有操作入口。
- 向 `/mk2/control_owner/set_moveit`（`std_srvs/srv/SetBool`）请求：
  `data=true` 申请 MoveIt，`data=false` 申请交还示教器。
  **返回 `success=true` 仅表示接受申请，绝不表示已完成交接。**
- 订阅 `/mk2/control_owner/state`（`std_msgs/msg/String`，JSON），
  等待目标 `owner`，同时查看 `reason`、`generation`、`native_sequence`、`fresh`。
  只有确认 `MOVEIT` 后才从 MoveIt 执行；只有确认 `PENDANT` 后才从示教器运动。

状态流：`UNAVAILABLE → PENDANT → ACQUIRING → MOVEIT → RELEASING → PENDANT`。
任意异常可进入锁存 `FAULT`，没有网络复位、自动恢复或自动重新申请。

## 顺序与保护

1. **申请 MoveIt**：要求反馈持续递增且新鲜（150 ms）、SDK 健康且已人工使能、
   `MoveState=0`，位置稳定至少 250 ms；若反馈带速度，还要求七轴速度足够低。
   实体还核对后端、固定配置路径、严格隔离标记和 DeviceConfig 指纹。
   先激活硬件，按最新测量位置初始化保持/命令及时间状态，再严格激活 JTC。
   两个服务成功且新的原生反馈为 active 后，才宣布 `MOVEIT`。
2. **交还示教器**：先结束/取消轨迹并确认停稳；接受、执行或取消中的目标会阻止释放申请。
   先严格停用 JTC，再停用硬件。驱动请求能力协商的 Release；原生执行
   `RobotStopRun`，核对停稳并成功 `ServoEnd` 后回 ready。
   硬件退出成功、ready 之后再有 250 ms 新鲜稳定反馈，才宣布 `PENDANT`。
3. 硬件生命周期通过专用 `/controller_manager/mk2_set_hardware_component_state`
   服务，与读/更新/写周期互斥。**只有没有命令接口占用的显式交接**允许暂停空闲周期，
   完成后重新建立采样时钟，避免把数百毫秒握手当作轨迹周期。
   正常控制 5..50 ms 时序检查、原生看门狗、速度/加速度/位置保护仍保留。
   不要绕过监督器直接调用普通 controller_manager 生命周期服务或手工激活 JTC。
4. 超时、响应拒绝/错误状态、序号倒退、反馈断流、SDK 故障或能力丢失均锁存，
   不会把失败释放标成 `PENDANT`。监督器退出会触发整个本机启动链路关闭，
   驱动走原有故障停止；不能据此认为实体已安全交还。
5. 不新增轨迹排队或重放。交接期间不要提交执行请求。
   全局 `/joint_states` 仍由独立纯 SUB 接收器发布，不用失效驱动的缓存冒充实测。
   整个启动链路已退出后，如需看示教器运动，另用只读 feedback 模式。

## 物理释放必须单独调试验收

[原生插件](mk2_control_plugin.c) 新增 `MK2_PHYSICAL_HANDOVER` 编译开关，
**默认 0**；只有同时选择物理构建并明确打开它，才接入 `RobotStopRun` 并声明交接能力。
原有默认物理构建仍不提供正常 Release，进入 ACTIVE 后的故障仍强停锁存。注意：物理
构建会在**首帧保持激活时**调用一次 `RobotStopRecover(0)` 清除启动前的强停锁存
（state 7），但这不是故障复位，也不上下电或清错。
隔离仿真插件也需更新到带新能力字段的版本，不能仅凭原有 clean-release 字段判定可用。

下一阶段必须先完成两个本机包（本包及配套 `je_software`）构建验证；
随后在操作员确认停机、退使能且机械可靠支撑后，另行授权备份/部署匹配插件。
应先做隔离 SDK 仿真联调，再分别验收实体接管保持、完成/取消目标后的交还、
示教器改变位置后重新接管、反馈丢失/故障/进程退出及独立急停。
SDK 注释说 `RobotStopRun` 可停止当前运动且不禁止后续命令，
但**这不是实体制动、安全停机或无抖动交接的验收证明**。
原生停稳阈值及时间是否适合实体噪声、SDK 的实际释放行为仍须现场验证，不能直接放宽。

这是**协作式软件仲裁**，不强制锁示教器界面，也不是经过认证的租约/会话隔离机制。
默认 ROS 服务和 ZMQ 不是认证授权边界；其它发布者或绕过流程的操作者仍可制造冲突。
`MOVEIT`、`ACQUIRING`、`RELEASING` 时禁止示教器点动/拖动；急停始终独立有效。
不要把两个入口在线等同于两路运动控制同时有效。

此前 MoveIt/RViz 退出过程的 SIGSEGV 尚未修复，本功能不宣称解决它。
