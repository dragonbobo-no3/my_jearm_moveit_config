# 控制丢失后的只读降级（2026-11-12，源码阶段）

## 本次实现范围

普通 `hardware_mode=control` 中，控制进程退出后不再立即关闭全部界面：

1. 原硬件故障保护仍先停止本机写入，控制管理器/JTC 退出。
2. 独立 SDK 状态接收器和机器人模型继续运行。
3. 只向旧 `move_group` 发送定向关闭请求并等待其实际退出。已启动的 RViz 客户端保持运行，不关闭重开。
4. 创建全新的 **只规划** `move_group`：`allow_trajectory_execution=false`，不带控制器配置。
	保留 `ExecuteTrajectoryAction` 接口，但执行请求明确以 `CONTROL_FAILED` 结束，不下发轨迹。
5. 不重启驱动，不清除原生故障，不重放旧目标，也不自动重新接管。

这是 **CONTROL_UNAVAILABLE → FEEDBACK_ONLY_LATCHED**，不是“示教器获权”。
此版本不再主动重启 RViz，后台规划服务仍有重建间隔，不是原生无缝交接。
若控制在首次前端调度前失败，只启动一次只规划服务和 RViz；若用户已关闭 RViz，不自动重开。
原 MoveIt/RViz 的析构崩溃未在本项目中修复；关闭超时沿用 launch 的进程退出升级，
25 秒仍未确认旧执行服务器退出则整栈关闭，拒绝并存两套执行服务器。
反馈断流仍终止当前栈，不能用冻结位置维持界面。用户主动关闭 launch 时不会启动新前端。
`shared` 分支仍保持原行为，本次没有把它扩展为自动点动抢占。

### 为什么保留 Execute 接口却仍禁止执行

MoveIt 2.5.9 的 `MoveGroupInterface` 构造函数同时等待 `move_action` 和
`execute_trajectory`；上一版禁用后者会导致 RViz 卡在连接阶段。已核对该版本上游源码，
且用本机安装的真实 MoveIt 验证：`allow_trajectory_execution=false` 时该接口直接
abort/`CONTROL_FAILED`，不会进入轨迹执行。接口存在不代表控制可用。
RViz 的 Execute 按钮可能仍显示；Plan & Execute 也可能只返回规划结果，不应据此认为执行成功。

保留窗口不意味着旧客户端目标已移交：控制丢失前正在等待的 goal 可能失去响应，
客户端忙状态如何恢复尚未实测；不自动重放该 goal。没有完成真实 RViz 窗口和实机点动验收。

## 正常交接与真实故障的边界

| 输入证据 | 当前处理 |
| --- | --- |
| 已有能力协商的显式释放流程，原生释放完成且新反馈停稳 | 既有 shared 策略允许完成交接；不等于点动自动接管 |
| 无交接请求却出现 `ready` / 失去 `active` | 未确认失权，保持故障处理，不能宣布 PENDANT |
| `state_error`、状态 7、掉电、驱动/运动错误、超时 | 故障锁存，停止执行；界面可进入只读降级 |
| 控制进程退出码 0 | 也不证明正常交接，只允许只读降级 |
| 故障后状态恢复健康 | 不自动清错、重新激活或恢复旧目标 |

**尚未完成的部分：**通过现有示教器点动键自动接管，以及点动结束后的 ROS 新会话再接管。
已部署的物理桥没有发布可靠的原生交接完成证据；已有隔离 SDK 实验的点动停止进入状态 7，
完整流程未通过。不能把 `MoveState != 13`、`ServoEnd()==0`、本机进程退出或界面存活作为原生
伺服线程已经退出的证明。仍需控制器侧经验证的正常切换判据和旧写入会话隔离。

## 安装与验证

新增 [退出屏障模块](../launch/mk2_control_fallback.py)，由原 CMake 的 launch 目录安装规则安装。
已有单文件符号链接不会自动安装新模块；需要重新构建/安装 `my_jearm_moveit_config`。
总入口会检查该模块，缺失时在启动节点前报错。无需因此重编 SDK 或部署控制器插件。
已安装且链接到源码的模块会随本次修改更新；当前运行中的 launch 不会热更新。
